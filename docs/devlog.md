# Devlog(開発ログ)

本家サイトの `/devlog`。その日に進んだことを、1日1件、短く書く。

## 記事の置き場所と形式

正本は `data/posts/*.md`。ビルド時に `frontend/src/lib/posts.ts` が取り込むので、バックエンドも DB も無い。
main へ push すると CI がビルドして公開される(= push が公開)。

ファイル名は `YYYY-MM-DD-<slug>.md`。slug は半角の小文字・数字・ハイフンのみ。
この形式に合わないファイルは記事として扱われない。**日付はファイル名が正**(並び順と表示に使う)。

```markdown
---
title: 記事のタイトル
summary: 一覧に出す1行の要約
projects: [vloom, hayabuzz]
---

本文(Markdown)。見出しは `##` から。
```

| キー | 必須 | 内容 |
|---|---|---|
| `title` | ○ | 無いと記事として扱われない |
| `summary` | | 一覧に出す1行 |
| `projects` | | 関連する作品の id(`data/projects.json` の `id`)。記事の頭に作品ページへのリンクが出る |

frontmatter は `key: value` と `[a, b]` の配列だけを読む簡易パーサ。YAML の入れ子や複数行は使えない。

## 何を書くか

**1記事で1つの作品を取り上げ、その作品に加えた更新を書く。** サイト自体の更新報告や、複数作品の変更の羅列にはしない。

- 材料はその作品のリポジトリのコミットと記録。何を変えたか、なぜか、測れるものは数字で
- 効かなかった試みや、はまった点も書く(読み物としていちばん面白いところ)
- 最後に残っている課題があれば一言

## 書くときのルール

- 本文に Markdown の表は使えない(`remark-gfm` を入れていないので描画されない)。箇条書きで書く

- **材料にしてよいのは、`data/projects.json` に載っている作品のリポジトリだけ。** 業務のリポジトリや未掲載のリポジトリの内容・名前は書かない
- 本リポジトリの記事は公開される。顧客名・ホスト名・パス・トークンなど、外に出せないものを書かない
- 1日1件。ミニマムでよい(数行〜)。何も進まなかった日は書かない
- 文体は作品ページの説明文に合わせる(だ・である調、短く、結論から)
- 画像を使うときは `frontend/public/devlog/<slug>/` に置き、`/devlog/<slug>/xxx.png` で参照する
